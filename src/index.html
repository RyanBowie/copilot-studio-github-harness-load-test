Capacity summary / what can be derived now

Window summaries use only contiguous, complete 60-second dispatch buckets within one cohort. They count the eventual outcomes of those requests at the original drain/cutoff, not replies completed inside the window. Never combine cohorts, bridge cooldowns, scale up a partial minute, or treat a burst as steady-state traffic. Different recorded configurations are ranked separately; unknown agent revisions still prevent a controlled comparison.

For each duration, the highest observed reply count and the highest zero-failure, zero-pending count are separate results. Ties prefer fewer failures, then fewer pending calls, then the earliest cohort and offset. An error-free segment inside an aborted trial is not a separately completed endurance test. A qualified calibration requires the existing 99% rule and full dispatch/drain; it is not a statistical guarantee or a capacity ceiling.

Sub-minute, rolling-window and completion-window maxima cannot be reconstructed from minute buckets. When present, the separately reviewed window supplement supplies them from existing private event evidence, without publishing that evidence or running new requests. Quota reset, recovery, longer endurance, representative workload reliability and settled unit costs remain unestablished. A later successful calibration alone does not prove recovery time or its cause.

Reviewed rolling windows and callback evidence

Supplemental windows are half-open [start,end), including the start and excluding the end. Dispatch-cohort maxima count eventual successful outcomes of requests dispatched inside the selected window. Completion maxima independently count successful native callbacks inside a window, including calls dispatched earlier. The two maxima need not share a run or window: both count types and exact boundaries are retained at each selected anchor.

Arrival-only coverage and observation through drain are separate choices. Through-drain peaks include time when no new requests were offered, not sustained offered load. Missing full coverage is unavailable, not zero; no partial window is normalized. Exact decimal strings preserve arithmetic on the original IEEE-754 clock values, not greater clock accuracy. Numeric display offsets are conveniences. Equal maxima retain the first reviewed representative; the window is not claimed to be a unique or earliest continuous optimum.

Selection is post hoc, not a new test or zero-error qualification. Boundary jitter and response-time variation can produce finite-window counts above nominal RPM. A chosen clean window cannot erase errors elsewhere or establish a quota. The burst lacks exact shared-origin completion offsets: adding its dispatch marker to separately clocked duration is only a lower bound, so exact burst completion-window maxima remain unavailable.

Failure snapshots count client callbacks after processing the specified event. Paced first errors and trigger callbacks have exact recorded offsets; actual dispatch-close assignments are bounded by synchronous callback and journal clocks, not directly timestamped. Burst first-error timing is bounded. Zero pending at the final cutoff describes recorded client invocation outcomes only: remote admission, work, retries and costs are not thereby settled. Costs remain pending and managed-service retry behaviour unknown.

01 / Identify the configuration without identifying people

Record published Teams, published Microsoft 365 Copilot or Studio Preview separately, along with known agent version, environment type, model, memory setting, workload, workflow and connector involvement. The harness label is GitHub Copilot Harness, not GitHub coding agent or Copilot SDK.

02 / Keep counting units separate

A run has one bounded timing window, not one session. An attempt is one sent user message or one native invocation on its labelled surface; runner retries are new attempts. Unsent drafts and unoffered/skipped client slots do not enter the denominator. Success means the requested outcome was returned: a visibly settled response in the Teams pilot, or a completed native invocation returning the requested greeting in the burst or paced campaign. It is not an independent general correctness evaluation or backend completion measurement. A failed requested operation can still produce a final explanatory message. Follow-up updates preserve the earlier cutoff snapshot rather than inventing missing timings.

Conversations are verified channel threads or Microsoft 365 conversation identifiers; sessions remain unknown unless independently observed. Failure payloads can contain valid conversation identifiers. They establish conversation identity, not proof of backend execution.

Each run record owns non-overlapping attempts. Update a pending run in place rather than appending another snapshot. Conversation and session counts are per-run and must not be summed as globally distinct counts.

03 / Measure only what is observable

The visible-message observation window starts at the first send and ends at the cutoff, including all measured completions; paced windows run from the cohort's monotonic start through drain/cutoff. First activity can be a status or an answer; first-answer timing excludes status text. Answer and UI-settled latencies use separate elapsed-millisecond samples and nearest-rank p50/p95 over timed completions. Activity timing may include pending turns without counting them as answered. UI settlement requires feedback controls plus the stated stable-text interval; it is an observation rule, not backend telemetry. Paced achieved dispatch rate uses its offer-window duration, excluding drain; neither that rate nor native completion durations establish steady-state capacity.

In-flight concurrency requires observed overlap between message send and terminal outcome. It does not establish simultaneous model execution. Report manual timing and partial windows explicitly.

04 / Do not treat Standard Harness as a controlled baseline

Tenant, Production versus Developer environment, old DirectToEngine versus the new channel transport, model and workload all confound that comparison. No Standard Harness measurements or images are reused here. A causal harness comparison requires a separately controlled experiment.

The separate Standard Harness report provides useful reporting patterns: explicit time windows, rate versus reliability, repeated endurance tests and failure analysis. Those patterns are not evidence for this agent's limits; send-window outcomes and completion-window throughput must remain distinct in either report.

05 / Review before publication

The public input is closed-schema, aggregate-only JSON. The report preparer's evidence and privacy review must exclude UPNs, tenant/environment/agent identifiers, internal URLs and citations, Teams/chat identifiers, connection details, credentials, raw transcripts and screenshots. Validation cannot prove review or an observation occurred. Report review does not attest to the separate workflow's human decision.

06 / Capture cost status from the first run

Every run records costs as pending, settled or unknown. Pending and unknown amounts stay null, not zero. Settled amounts identify currency, evidence source and whether attribution covers this run or a shared window. Shared-window costs and different currencies are never summed.
