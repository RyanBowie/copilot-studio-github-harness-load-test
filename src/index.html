Evidence before scale.

Only explicitly reviewed aggregate facts belong here. Missing evidence is not a zero, a successful test, or an absence of throttling.

What this study measures

Single authenticated account, labelled channel surface, observed message outcomes and visible response latency. Runs, conversations and sessions remain distinct units.

What this study does not claim

A single Teams bot chat can serialize turns. Its behavior alone cannot establish platform-wide capacity, backend parallelism or a universal service limit.

Response time

Elapsed time from message send to first visible response and, separately, UI settlement. Settled means feedback controls are present and text remains unchanged for the recorded stability interval. Neither endpoint is backend completion, time to first answer (TTFA) or first token.

Read the sample, not just the percentile

Latency samples cover successful, completed messages only. Failed, pending and untimed messages are excluded and remain visible in the run counts. Percentiles are never pooled across runs; small samples do not establish stable tail behavior.

Throughput & limits

Observed arrivals, in-flight message overlap and completions describe a measured window, not a platform capacity ceiling. Unobserved rate and concurrency remain not measured.

Documented numerical limits

Documentation is a separate evidence class, never an observed result. Applicability to the tested configuration must be reviewed explicitly.

Stages & observations

Sent message attempts are classified as completed, failed or still pending at the observation cutoff. Unsent drafts are separate client setup issues, excluded from message outcomes. There is no inferred backend stage timeline.

A failure category is not a root-cause claim

Classification follows reviewed visible errors or transport status. Unknown failures stay unknown; slow replies alone are not evidence of throttling. Pending turns are not silently converted into timeouts or successes.

Methodology & boundaries

A reproducible public summary, not a transcript archive. Raw evidence stays outside this repository; every published measurement requires human review.

01 / Identify the configuration without identifying people

Record published Teams versus Studio Preview, agent version when known, environment type, model, memory setting, workload, workflow and connector involvement. The harness label is GitHub Copilot Harness, not GitHub coding agent or Copilot SDK.

02 / Keep counting units separate

A run is one bounded observation window, not one session. An attempt is one sent user message; retries are new attempts. Unsent drafts do not enter the agent denominator. Completed means a successful, visibly settled response, not verified answer correctness or backend completion. Conversations are channel threads; sessions are runtime sessions only when observed, never inferred from conversations.

Each run record owns non-overlapping attempts. Update a pending run in place rather than appending another snapshot. Conversation and session counts are per-run and must not be summed as globally distinct counts.

03 / Measure only what is observable

The observation window starts at the first send and ends at the cutoff, including all measured completions. First-visible and UI-settled latencies use separate elapsed-millisecond samples and nearest-rank p50/p95 over timed completions. UI settlement requires feedback controls plus the stated stable-text interval; it is an observation rule, not backend telemetry. Completion pace is completed messages divided by the full observation window; arrival rate uses its separately observed arrival window. Neither is a steady-state capacity estimate.

In-flight concurrency requires observed overlap between message send and terminal outcome. It does not establish simultaneous model execution. Report manual timing and partial windows explicitly.

04 / Do not treat Standard Harness as a controlled baseline

Tenant, Production versus Developer environment, old DirectToEngine versus the new channel transport, model and workload all confound that comparison. No Standard Harness measurements or images are reused here. A causal harness comparison requires a separately controlled experiment.

05 / Review before publication

The public input is closed-schema, aggregate-only JSON. Human review must exclude UPNs, tenant/environment/agent identifiers, internal URLs and citations, Teams/chat identifiers, connection details, credentials, raw transcripts and screenshots. Validation is defense in depth, not an anonymizer or proof that an observation occurred.

06 / Capture cost status from the first run

Every run records costs as pending, settled or unknown. Pending and unknown amounts stay null, not zero. Settled amounts identify currency, evidence source and whether attribution covers this run or a shared window. Shared-window costs and different currencies are never summed.

Future scope: email → workflow → agent. That scenario is not implemented or measured by this scaffold.

Costs, tracked from the outset

Billing evidence may lag the load observations. Unsettled cost is not free usage, and missing attribution is not a per-message price.

No implied total or unit cost

This report presents settled amounts per evidence scope, without combining currencies or shared billing windows. A verified zero is allowed only with settled billing evidence; pending and unknown states never display a currency amount.
